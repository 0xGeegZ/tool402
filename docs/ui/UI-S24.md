# UI-S24 dashboard workspace reconciliation manifest

## Purpose

UI-S24 is an early truth-first POLISH slice for the guest workspace route
(`/dashboard`). It follows accepted UI-S22 and uses only the already recorded
`PREP-UI-001` workspace visual slice as its comparison authority. It does not
replace the dashboard with a new concept or import a complete source tree.

The slice must make the current workspace understandable at first glance: what
the surface is for, which local journeys are available, what a visitor can do
next, and which capabilities are deliberately unavailable. It retains
compatible visual hierarchy, illustration language, branding, spacing rhythm,
section composition, and responsive intent where they agree with the
demonstrated product. Every route, CTA, label, and state instead reflects only
current local truth.

## Trigger and order

`D-S24-010-002` supersedes only the former start-order condition: this slice
may begin before the first complete Provider campaign / ATS rehearsal and before
S22 acceptance. The pending Stage B human gate remains a hard truth filter: no
claim may imply an account, wallet, provider, balance, payment, transaction,
receipt, evidence, availability, funding, return, or live capability that
current local evidence does not independently support. Stage B remains required
before a human-owned public deployment or demo-video action uses the dashboard.

## Required comparison before source work

Before a readiness review selects any source path, the root must:

1. inspect the current `/dashboard` route in desktop and narrow viewport
   states;
2. compare only the selected `PREP-UI-001` workspace visual slice through the
   existing local source workflow;
3. amend the local UI-S24 ledger with compatible sections, local assets, exact
   source/test paths, and the current local route target for every CTA; and
4. record each omitted element and the truthful reason it cannot appear today.

This comparison is a focused design translation. It cannot reopen the accepted
Dashboard route contracts, turn a guest surface into an account dashboard, or
substitute fabricated states for a rehearsed flow.

## Allowed outcome

After its own readiness, RED, GREEN, review, and verification cycle, UI-S24
may improve the current guest workspace with:

- a clear workspace purpose and a visible hierarchy of local journeys;
- truthful next-action and unavailable-state guidance;
- compatible local visual assets, typography, spacing, panels, and responsive
  composition; and
- CTAs that map only to committed local routes and preserve editable, inert
  form behavior until a visitor explicitly acts.

## Exclusions

UI-S24 must not create an authentication, session, account, wallet, provider,
balance, client-data, runtime-configuration, payment, transaction, evidence,
or live-status surface. It must not add a mock adapter, automatic request,
analytics, hosted font, external link, fabricated metric/testimonial/claim,
deployment, or video behavior. It must not redesign from scratch or import a
bulk archive.

No source path, asset, dependency, or test is authorized by this manifest
alone. The activation record authorizes only focused RED tests; source remains
prohibited until a later independent RED review accepts exact GREEN paths.
